description: The Velopulent CMS data-plane contract across REST, GraphQL, gRPC, and MCP.

Velopulent CMS exposes one site-scoped content model through four protocol adapters. Dashboard configuration and instance administration remain under `/api/dashboard/*`; they are not public data-plane APIs.

| Capability | REST | GraphQL | gRPC | MCP |
| --- | --- | --- | --- | --- |
| Sites and site info | Yes | Yes | Yes | Yes |
| Collection/schema discovery | Yes | Yes | Yes | Yes via resources |
| Collection/status/search queries | Yes | Yes | Yes | Yes |
| Entry CRUD | Yes | Yes | Yes | Yes |
| Publication lifecycle | Yes | Yes | Yes | Yes |
| Singletons and revisions | Yes | Yes | Yes | Yes |
| File metadata/references | Both | Both | Both | Metadata |
| Upload initiation | Multipart + signed URL | Signed URL mutation | Client streaming | Signed URL tool |
| Binary delivery | HTTP | URL | URL | URL |
| Schema mutation, webhooks, deployments, backups, members, tokens | Dashboard-only | Not exposed | Not exposed | Not exposed |

All public requests use scoped `vcms_site_*` keys or `vcms_pat_*` personal tokens. Personal tokens require an explicit site context. Draft queries require `content.preview.read`; publication requires `content.publish`.

Entry and singleton updates accept an opaque expected version. Entry versions advance on every write and are checked atomically in the database. REST entry and singleton reads return `ETag`; updates accept `If-Match`. Publication, deletion, and revision restoration do not yet expose expected-version inputs.

## MCP

The MCP server implements the dated `2026-07-28` protocol with `rmcp 3.3.0`, stateless Streamable HTTP, `server/discover`, per-request metadata, structured tool output, resource templates, resource cache hints, and stdio proxy forwarding. It intentionally advertises no OAuth metadata, prompts, tasks, subscriptions, sampling, roots, logging, or elicitation: public CMS workflows do not need those capabilities. VCMS bearer credentials and `mcp.use` are the explicit provisioned-token mode.

Schema and content discovery is available through `cms://{site_id}/schema`, collection templates, and singleton templates. Read resource access is independently authorized for schema and content.

## Implementation limits

The API adapters share domain services and authorization policy, but domain services still serve trusted dashboard and offline callers without taking a principal. Authorization is enforced by each external adapter. This is not yet the principal-bound application layer proposed in the architecture plan.

Structured query support is limited to collection, publication status, and search. General schema-field filters, custom sorting, projection, protobuf FieldMask updates, and Relay cursor inputs are not implemented. GraphQL rejects unsupported filter/order inputs. REST and gRPC signed page tokens bind queries but still use offsets internally; concurrent writes can shift pages.

The gRPC contract retains legacy JSON text and numeric pages alongside typed fields. Protobuf Struct represents numbers as doubles; use JSON text fields when exact large-integer precision matters. MCP uses `list_entries` rather than the proposed `query_entries`. Media URLs remain public by opaque ID; metadata access does not confer confidentiality on binary delivery. OAuth remains an intentional gap.

Existing cross-site ownership inconsistencies cause the API migration to fail. It preserves those records rather than silently deleting or reassigning them; back up and repair invalid legacy records before upgrading.

Read scopes govern discovery and read operations. Mutation scopes also authorize their returned representations; a write-scoped token is not a confidentiality barrier against its mutation targets. Restore refreshes operational entry versions rather than reusing archived ETags.
